# SentinelReview Threat Model

This document outlines the security architecture, trust boundaries, and threat vectors for the SentinelReview system using the STRIDE methodology.

## System Actors and Trust Boundaries

- **Untrusted Users/Code**: The developers submitting GitHub Pull Requests. Their code is considered actively hostile.
- **Semi-Trusted Entity**: The GitHub API (Webhook Source). We trust the HMAC signature to verify origin, but the payload contents (the diff) belong to the untrusted user.
- **Fully Trusted Boundaries**: The FastAPI backend, the PostgreSQL database, the Redis message queue, the RAG knowledge base.
- **Isolated Execution Environment (Sandbox)**: The ephemeral Docker environments where untrusted code is compiled, dependencies are installed, and tests are executed during the Verification stage.

## STRIDE Analysis

### 1. Spoofing
- **Threat**: An attacker forges a GitHub webhook to trigger arbitrary reviews or exhaust resources.
- **Mitigation**: All incoming webhooks to the Triage Agent are strictly verified using the GitHub HMAC-SHA256 signature against the configured `GITHUB_WEBHOOK_SECRET`.
- **Threat**: An attacker spoofs another user's dashboard session.
- **Mitigation**: Dashboard access requires GitHub OAuth. The backend issues secure, `HttpOnly`, `SameSite=Lax` JWT session cookies, heavily mitigating XSS-based token theft.

### 2. Tampering
- **Threat**: An attacker modifies the generated Patch Suggestion before it gets committed to the PR.
- **Mitigation**: Patch suggestions are generated by the Fix Agent, passed securely through the internal LangGraph state, saved to PostgreSQL, and posted directly to GitHub by the Reporting Agent. There is no user-accessible endpoint to mutate a patch in transit.

### 3. Repudiation
- **Threat**: An administrator claims the system took an action (or failed to) without proof.
- **Mitigation**: The `AgentRun` table records every single state transition in the LangGraph pipeline. Inputs, outputs, prompt versions, token counts, and error states are immutably logged for audit purposes.

### 4. Information Disclosure
- **Threat**: An attacker writes a malicious PR specifically designed to trick the LLM (Prompt Injection) into exfiltrating internal prompts or environment variables.
- **Mitigation**: The Triage and Fix Agents utilize the `app/security/guardrails.py` system. The untrusted PR diff is heavily sanitized. Furthermore, the LLMs executing the prompts do not have shell or network access, and the system relies on structured JSON outputs preventing arbitrary leakage.

### 5. Denial of Service (DoS)
- **Threat**: An attacker submits a massive PR (100k lines) to exhaust LLM API limits and database storage.
- **Mitigation**: The Triage Agent inspects diff size and rejects PRs that exceed a predefined threshold before they hit the expensive LLM stages.

### 6. Elevation of Privilege (Arbitrary Code Execution)
- **Threat**: An attacker submits a PR with a malicious `setup.py` or malicious test suite designed to take over the SentinelReview backend during the Verification stage.
- **Mitigation**: The Verification Agent executes all generated patches and tests inside a locked-down, network-isolated, ephemeral Docker sandbox (or equivalent isolated runner). 
- **Threat**: The Static Analyzer (`bandit`/`semgrep`) is exploited via a malformed source file.
- **Mitigation**: Subprocesses (`subprocess.run`) are strictly called with `shell=False` and arguments are isolated. The static analysis is run purely statically; the code is never executed during this phase.

## High-Risk Areas & Future Work

- **LLM Prompt Injection**: This remains the hardest vector to categorically solve. While we sanitize inputs, the Fix Agent must interpret the untrusted code to fix it. Relying on bounded output parsing and sandbox verification ensures that even a hijacked LLM cannot execute code on the backend host.
- **Verification Sandbox Escape**: If the ephemeral test sandbox is compromised via a zero-day container escape, the host could be at risk. Hardening the verification container (e.g., using Firecracker microVMs or rootless Podman) is a recommended next step for multi-tenant production deployments.
